# Surfboard 兼容性排查记录

> 排查对象：本仓 Surge 配置（懒人版 / 分流版）导入 Android 客户端 Surfboard。
> 排查日期：2026-10-07。结论：**报错全部来自 `policy-path` 订阅地址这一行**。
> ⚠️ 订正（2026-10-10）：初版此结论含「配置语法本身没有阻塞项」——后半句不准确：
> 语法上确有多处 Surfboard 不支持的构造（见 §3.4），只是它们未表现为导入报错。
> 以下是完整过程与证据，供日后复用。

---

## 0 · 结论速览

| 现象 | 真因 |
|:--|:--|
| `connection closed` / `HTTP 400` / `HTTP 404` | `policy-path=` 指向的订阅地址拉取失败；Surfboard 导入时会**真去请求**，失败即中断，不给友好提示 |
| `fetched policy-path content is invalid` | 拉到了，但内容格式不是 Surge policy-path 形态（典型是 Clash YAML / base64 节点串） |
| 导入成功但没有节点 | 机场识别出客户端后返回空响应（常伴随「不支持你使用的客户端」提示） |

**一句话**：不是配置写错了，是订阅地址必须能在导入时被成功拉取、且返回 Surge 格式。

---

## 1 · 排查方法：控制变量二分

不要一次改一堆东西。做法是「最小可导入骨架 → 逐层加回」。

### 1.1 最小骨架（验证客户端本身可用）

```ini
[General]
loglevel = notify

[Proxy Group]
Proxy = select, DIRECT

[Rule]
FINAL,Proxy
```

→ **通过**。说明 Surfboard 与本地导入路径都正常，问题在配置内容。

### 1.2 逐层加回（每步只加一个变量）

| 步骤 | 加了什么 | 结果 |
|:--|:--|:--|
| D1 | `dns-server` 一行 | ✅ 通过 |
| D1b | 首行 `#! version=` + 长注释块 | ✅ 通过 |
| D2 | 完整策略组（smart / include-other-group / policy-path） | ❌ connection closed |
| D3a | 只留 `select` + Airport 槽（无 policy-path） | ❌（注：此步仍带 policy-path，见下） |
| D3b | 只留 `smart` + Airport | ❌ |
| D3c | 只留 `include-other-group` | ❌ |
| D4a | 纯 select + DIRECT/REJECT，无任何订阅 | ✅ 通过 |
| D4b | 有 Airport 组但**不带** policy-path | ✅ 通过 |
| D4c | Airport **带** policy-path（假 token） | ❌ connection closed |
| D5 | policy-path 指向普通可达地址 | HTTP 400 |

**分水岭在 D4b ↔ D4c**：唯一变量就是 `policy-path=` 这一行。

D3a/b/c 三组同时失败曾被误读为「smart 或 include-other-group 不被支持」——
实际是三个样本里都保留了 policy-path，共同变量没被隔离。**教训：切片测试必须确认
共同变量，否则会把无关项当成元凶。**

## 2 · 被证伪的几个猜想

排查中先后怀疑过，均**已证伪**（记录在此以免重走）：

| 猜想 | 证伪方式 |
|:--|:--|
| `smart` 组类型不支持 | Surfboard release notes 明写 `Support Smart proxy group type(fallback to auto)` |
| `include-other-group` 不支持 | 去掉 policy-path 后同样写法可导入（D4b 变体） |
| `[URL Rewrite]` 段导致硬拒 | 整段删除后仍报同样错误 |
| `[SSID Setting]` 段导致硬拒 | 同上 |
| 规则行上的 `pre-matching` / `extended-matching` 参数 | 删除后仍报同样错误 |
| 首行 `#! version=` 被当成特殊指令 | 改成普通注释后仍报同样错误 |
| 订阅节点协议 hysteria2 不支持 | release notes 明写已支持 Hysteria2 |

⚠️ **官方 manual（manual.getsurfboard.com）最后更新于约 4 年前**，其「支持的协议」
「受限不支持的功能」两节已严重过时。判断能力边界应查
[GitHub Releases](https://github.com/getsurfboard/surfboard/releases)，不要信 manual。
→ 已整理为 [`docs/02-官方更新日志.md`](02-官方更新日志.md)（能力时间线 + 旧结论订正）。

⚠️ 权威语法参考（2026-10-10 新增）：官方 AI Profile Guide 的
[Profile Syntax Reference](https://getsurfboard.com/docs/ai-profile-guide/reference)
声明「提炼自解析器源码，未收录即不支持」—— 判断某个构造是否合法，这是最高权威，
优先级高于 manual、release notes 和社区配置。详见 §3.4。

## 3 · 已知能力差异（2026-10-07 查证）

### 3.1 不支持的项

- **`icon-url`** — 策略组与节点的图标键不认，写了会被忽略（不是报错）。
- **`[URL Rewrite]` 段** — 官方明示不支持。
- **`[SSID Setting]` 段** — 无此概念（它有自研的 `subnet` 组类型，语法不同，2.34.1+）。
- **规则类型 `URL-REGEX`** — 官方明示不支持。
  > ⚠️ 订正（2026-10-10）：`USER-AGENT` 规则**已于 mobile-2.29.2 支持**（按 User-Agent
  > 通配匹配路由 HTTP 流量，要求 Android 10+ 且开启 VPN HTTP Proxy）。初版此处写
  > 「USER-AGENT / URL-REGEX 均不支持」，前半段已被 release notes 证伪。
- **MITM** — Android 平台限制。

### 3.2 支持但要注意

- `smart` 组类型 → **自动降级为 auto（url-test 语义）**，不会报错。
- `policy-path` + `update-interval` → 支持，且会自动后台刷新。
- `RULE-SET` 的 `update-interval` → 支持。
- Hysteria2 / AnyTLS / Snell / SS2022 / WireGuard / TUIC v5 → 新版均支持。
- `underlying-proxy` 链式代理 → 支持。

### 3.3 Surge 4/5 专有 `[General]` 键

以下键在 Surfboard 侧无对应实现（多数被静默忽略，非报错）：
`encrypted-dns-server`、`encrypted-dns-follow-outbound-mode`、`allow-dns-svcb`、
`udp-priority`、`wifi-assist`、`all-hybrid`、`gateway-restricted-to-lan`、
`proxy-restricted-to-lan`、`disable-geoip-db-auto-update`、`ipv6-vif`、`proxy-test-udp`、
`show-error-page-for-reject`、`exclude-simple-hostnames`、`read-etc-hosts`、
`use-local-host-item-for-proxy`。

> ⚠️ 订正（2026-10-10）：初版此列表还含 `block-quic` —— **已误伤**。mobile-2.31.1 起
> Surfboard 支持代理参数形式的 `block-quic`（写在代理行上，非 `[General]` 键）。
> General 级同名键仍无对应实现。转换脚本删除的是 General 键，不受影响。

> 未逐项实测哪些是「静默忽略」哪些是「报错」。目前证据只支持：**它们不是本次
> 阻塞的原因**（D1/D1b 只带 dns-server 即可通过，整份配置删光这些键仍失败）。

### 3.4 权威语法参考与配置修复（2026-10-10）

官方 [Profile Syntax Reference](https://getsurfboard.com/docs/ai-profile-guide/reference)
（AI Profile Guide 的附录，声明「提炼自解析器源码 surfboard-core/profile/；未收录即不支持」）
与本仓 profile 对照后，确认以下构造**不被支持**，已在两个 profile 与转换脚本中修复：

| 构造 | 官方口径 | 处置 |
|:--|:--|:--|
| `RULE-SET,SYSTEM` / `RULE-SET,LAN` | RULE-SET 只接受远程 http(s) URL；内置集名明示不支持 | SYSTEM → 改引本仓自托管快照 `apple_system.list`；LAN → 14 条内联 IP-CIDR 展开 |
| `FINAL,{policy},dns-failed` | FINAL 只接受 `FINAL,{policy}` | 删修饰参数 |
| `no-resolve` 于 RULE-SET 行 | 仅 IP-CIDR / IP-CIDR6 / GEOIP 接受 | RULE-SET 行全部删除（含 IP 的集在 Surfboard 侧会被强制解析一次，引擎限制无法规避） |
| `[General]` `hijack-dns` | 键表未收录 | 删除；硬编码 :53 查询改由 GEOIP 非 CN → 代理兜底，泄露面仍为零 |
| `[General]` `loglevel` | 键表未收录 | 删除 |
| 策略组 `policy-priority` | 参数表未收录 | 删除（低倍率加权仅 Surge 侧生效） |

> 语法参考同时确认：`no-resolve` 于 IP 类规则合法（兼容保留）；`policy-regex-filter`
> 默认 `.*`，对 policy-path / include-all-proxies / include-other-group 拉入的成员生效；
> 测试 URL 必须 http://（https 是解析期错误）；未知策略名在导入时硬拒。

## 4 · 订阅格式：最容易踩的坑

`policy-path` 要的是 **Surge 格式的节点列表**，一行一个，形如：

```
ProxyHTTPS = https, 1.2.3.4, 443, username, password, sni=www.google.com
```

而机场订阅常见三种返回，未必都对得上：

| 机场返回 | Surfboard 反应 |
|:--|:--|
| Surge 格式 | ✅ 正常导入 |
| Clash / mihomo YAML | ❌ `fetched policy-path content is invalid` |
| base64 节点串 | ❌ 同上 |
| 按 UA 判断、识别不出就给空 | ❌ 无报错但无节点，或提示「不支持你使用的客户端」 |

**很多机场不提供独立的 Surge 订阅链接。** 实测同一账号下多个订阅地址，
只有一个能用于 Surfboard —— 试出哪个可用后记住它即可。

## 5 · 导入前的自检清单

1. 订阅地址在浏览器里打开，返回的是不是 Surge 格式的节点行？
2. 该地址是否需要代理才能访问？（Surfboard 导入时可能尚未连通，会失败）
3. 本地文件导入也失败时，先确认是不是同一份文件在 URL 导入也失败 —— 排除网络因素。
4. 报错只有 `connection closed` 两个词时，**优先怀疑订阅拉取**，不要去翻配置语法。

---

## 6 · 与 Surge 侧的能力差（选型参考）

Surfboard 的定位是「兼容 Surge 配置」，实际是**兼容子集**：

- 继承了 Surge 的语法约束（如不支持 VLESS），同时也继承了部分限制；
- Surge 4/5 新增的 DNS 加固键、URL Rewrite、SSID 自动化等均无对应实现；
- 好处是策略组语义（select / url-test / fallback / smart）与规则集机制基本可用。

若目标是安卓端完整体验，mihomo 系（Clash Meta 内核）在协议覆盖与配置自由度上
明显更宽；若已有 Surge 配置资产、只求复用，Surfboard 是可行的折中。
